# Architecture

## Config
- `config/universe.yaml`: everything tracked: ETF groups, stock lists, macro tickers, CFTC/OECD sources, the watchlist, and `sector_etfs` (the sector ETF a stock is compared with on its profile, by Yahoo sector, with industry overrides). Theme ETFs carry a UCITS `isin`, checked against `imports/positivliste.xlsx` (SKAT list; only the latest year's sheet counts).
- `config/settings.yaml`: thresholds (regime, momentum, rotation, stops, coverage limits).
- `config/views.yaml`: market-view templates (ready-made beliefs with exposures and indicators, opposite pairs) and the indicator catalogue the evidence check can read (relative strength, ratios, FRED changes, OECD CLI). `universe.yaml` `macro.fred_views` holds FRED series only the views read (kept out of the regime's freshness check).
- `config/settings.yaml` `network:` and `ops:`: per-host request limits (rate, burst, concurrency, retries, soft daily budget, cooldown after repeated 429s) and how long the operations log keeps its rows.
- `config/discovery.yaml`: the discovery scan: markets (exchanges, size floors, minimum counts, an optional `index` whose members are always kept, `members_only` for an index-only market such as the S&P 500), size and liquidity thresholds, flag settings, ETF listing preference and the name → category table.

## `src/radar/`
- `updater.py`: the update steps behind `radar update`/`run` (each source logged, failures keep the cache; each step's requests carry its source key) and the background job the app's *Update data* button runs (recorded as a job in `ops`). `health.py`: `radar doctor`.
- `net.py`: the one network layer. `net.get` (plain HTTP: every `requests` call site uses it) paces each host with a token bucket and a concurrency cap (settings.yaml `network.hosts`, glob patterns, hosts under one pattern share them), records the request in `ops`, and retries 429/5xx/timeouts with exponential backoff and `Retry-After`; other answers are returned for the caller to judge (`expected` statuses, such as a probe's 404, aren't counted as errors). `install_yfinance()` / `net.yf()` make yfinance's single shared session (`YfData`) a recording, rate-limited curl_cffi session and keep it there (yfinance would otherwise swap in a fresh one per `download`/`Ticker`/`Search`/`screen`); yfinance keeps its own retries. Repeated 429s pause a host (`Throttled`, stored in ops.db so the CLI and the server share it). `net.pool(n)` is a thread pool capped at the host's concurrency whose tasks keep the caller's ops context. One honest User-Agent; no proxies or identity rotation.
- `ops.py`: the operations log in `data/ops.db` (SQLite, WAL, its own `user_version` migrations, no backups: it can be deleted). Tables: `requests` (host, redacted path, status, ms, bytes, attempt, source, job), `events` (info/warn/error × source/parse/api/job/throttle/doctor, with a capped traceback), `jobs` (update, discover and CLI runs with their log), `host_state` (cooldowns). `ops.context(source=, job=)` attributes what happens inside; threads that libraries start fall back to the one source/job active in the process, if there is exactly one. Writes never break the work (a failed write is a warning on the `radar.ops` logger). Pruned after each job and at server start (`ops:` in settings.yaml). Feeds the Operations page and `radar ops`; nothing here feeds a market reading.
- `ingest.py`: yfinance prices and FRED series → `data/*.parquet`. `config.write_parquet` writes atomically, so a running server never reads a half-written file. The price history starts at `universe.history_start()` (`history_years` back, or `backtest.warmup_days` before your first trade, capped at `backtest.max_years`); a stored history that starts later is downloaded again in full once, and `data/prices_from.json` remembers each ticker's download start.
- `external.py`: CFTC positioning, OECD leading indicators, the FactSet Earnings Insight PDF, Yahoo analyst consensus for holdings and watchlist, and Yahoo ticker detail (`fetch_detail` / `detail`, cached in `data/profiles/`).
- `universe.py`: config access, S&P 500 constituents (SSGA SPY holdings), names, currencies, sectors, positive list; `transactions()`/`ledger()`/`holdings()` from the store for a portfolio selection (default: your real portfolios; average-cost `replay`, `positions` per portfolio), `fx_to_dkk`, the Yahoo import, and the one-time move of the old `imports/*.csv` into the store (`ensure_migrated`).
- `signals/`: `risk.py` (weekly DKK beta ± se, alpha, downside beta, Sharpe/Sortino, drawdowns, factor tilts, correlations, risk budget), `gauges.py` (graded readings), `rotation.py` (RRG), `momentum.py`, `regime.py`, `levels.py` (rule-based trailing ATR stop / take-profit with reasons, for held stocks, theme ETFs and ticker profiles), `technicals.py` (RSI, MACD, Bollinger, volatility, drawdown, beta).
- `dashboard.py`: every market-wide reading as data (regime with chart series, rotation with RRG tails, momentum leaders, positioning, coverage). `compute()` has no side effects; `load()` reads `reports/dashboard.json` for the API.
- `report.py`: `radar report` writes `dashboard.json` and the compact `summary.json` (a contract with the skills: its keys don't change without them), then the rank snapshots.
- `mine.py`: the holdings/watchlist/sold table (DKK return vs a shadow ACWI position, flags, stop levels), pooled over a portfolio selection (default: your real ones). `radar run` uses it for summary.json; the API recomputes it live.
- `performance.py`: portfolio returns over time: a daily DKK value per portfolio (`book`), the time-weighted index (`twr`), XIRR (`xirr`), ACWI over the same period and with the same flows, `analyze` (series + stats), `compare` (portfolios and pooled tag groups from a common start) and `summary` (summary.json's `portfolios`). Also the cash helpers (`cash_moves`, `cash_balance`, `trade_cash_dkk`).
- `simulate.py`: virtual portfolios for A/B tests: `fork` (a copy of a portfolio at a day's close) and the interface simulations write through (`Strategy`, `new_sim_portfolio`, `write_run`: a checked, idempotent run per simulated portfolio; `find_sim` by parent and strategy).
- `backtest/`: point-in-time backtests on your own trades. `pit.Context` gives the stop/take-profit rule's inputs as known on a past day (metrics via `momentum.metrics_panel`, the universe percentile, the weekly regime with publication lags, analyst rows fetched by then, ATR). `exits.replay` walks the sessions (rule fills, your rows, the rule at the close) for the `overlay` and `rules` variants; `exits.refresh` writes one sim portfolio per real portfolio and variant (tags `exits-overlay` / `exits-rules`) and `reports/sim-exits.json`. `radar sim exits`.
- `userstore.py`: the user's own edits in `userdata/radar.db` (SQLite, versioned with `PRAGMA user_version` + `MIGRATIONS`). Tables: watchlist adds/removes (an overlay `universe.holdings()` applies), portfolios (real or virtual, tax kind, dividend policy, origin manual/fork/sim) with portfolio_tags, transactions (trades and cash rows, each in a portfolio: the source of truth), sim_runs, imports (undoable as a whole, into a portfolio), symbol_map (remembered broker identifier → Yahoo symbol), meta. A backup goes to `userdata/backups/` before imports, undos, moves and schema upgrades; a migration step may be a tuple of statements that runs as one unit (for rebuilding a table). `portfolio_ids()` is the one place that decides which portfolios count: real ones that aren't archived, unless ids or tags are chosen. New stateful data (notes, targets, alarms) gets a new table here.
- `portfolio.py`: checks a row before it is saved (trades: unknown symbol, future date, oversold in its portfolio, price vs that day's close; cash rows: amount in DKK; negative cash is an error in a virtual portfolio and a warning in a real one with a cash ledger), its effect on the position, moves between portfolios (`check_move`); the Portfolio page's positions and cash view.
- `importers/`: broker exports → trades: reading CSV/XLSX in any encoding, presets in `presets.yaml`, generic column names, symbol matching, `preview` (never writes) and `commit`.
- `snapshot.py`: rank history for "new" and "Δ rank".
- `valuation.py`: the weekly valuation snapshots in `data/valuation/` (stocks from Yahoo's screener, `stocks.parquet`; ETFs from Yahoo fund data, `etfs.parquet`) and the market's valuation (`market.parquet`: CAPE from multpl.com, Damodaran's ERP). `Context` / `context()` join them to table rows (P/E vs sector, EPS revisions, fund P/E vs ACWI) without network calls. `signals/valuation.py`: the readings (pure functions). `sentiment.py`: CBOE put/call (`data/putcall.parquet`) and the AAII survey (`data/aaii.parquet`). `external.update_ecb`: euro-area yields (`data/ecb.parquet`).
- Regime votes: `dashboard.effective_votes()` (settings.yaml `regime.votes` overridden by `userstore` meta `regime_votes`), `dashboard.regime_now()` (the stored indicators voted again) and `vote_options()`; `GET/PUT /api/settings/regime-votes`.
- `market_views.py` + `signals/views.py`: your market views (subjective beliefs, stored in `userstore`). `evidence` marks each view's indicators supports / contradicts / flat / no data from the last three months; `align` says how a name lines up (exposure by ticker, sector, industry, region, or a ≥0.5 correlation of weekly returns vs ACWI with an ETF), conviction-weighted. Personal: in profiles only when not anonymous (`radar info A B` only with `--personal`), and in the holdings bundle as `views.json`.
- `discovery/`: the separate wide scan. `sources.py` (Yahoo screener per exchange and per sector, cross-listing removal, index members from iShares holdings (STOXX 600 via EXSA, S&P 500 via CSPX), positive-list ISIN → Yahoo ETF mapping, share-class choice, ETF categories; every source checks its counts and raises), `scan.py` (universe cache `data/discovery/universe.csv`, its own price store `data/discovery/prices.parquet` re-downloaded each scan with retries for Yahoo's rate limit, `reports/discovery.json`, snapshots in `data/discovery/snapshots/`). `signals/discovery.py` scores each market with the momentum formula and adds Δscore, size, liquidity and flags. Nothing here feeds the regime, breadth or the momentum page; `coverage.py` shows its age on the Data page without counting it in "oldest input" or stale sources.
- `coverage.py`: per-source freshness and coverage, the update log `data/sources.json` (written atomically under a lock; each attempt is also an `ops` event, a ValueError a parse failure), and blind spots. `live()` overlays the current log on a built coverage section (`/api/coverage`). These feed the "Data & coverage" page and `coverage` in summary.json. Stale sources and missing inputs are shown but don't vote; limits are in `settings.yaml` `coverage:`.
- `profile.py`: one ticker's full profile (used by `radar info` and the API), including the risk section; `compare()` puts several side by side with ACWI (`radar info A B`, the `/compare` skill).
- `guide.py`: the Danish books in `guide/` (see below): the manifest `guide/guide.yaml` (books → parts → chapters, `page_links`, `glossary_links`), one chapter per file reached only through the manifest, `{{settings:key}}` placeholders filled from settings.yaml (`|pct`, `|raw`), heading ids (one slug rule, used by the page and by links), prev/next and a section search.
- `notebook.py`: the Notebook page's read-only view of what the skills write: `briefs/`, `research/` (+ `compare/`) and `journal/` (+ `reviews/`), with journal front matter (status, account, review date) parsed and *review due* worked out; documents are reached only through the listing.
- `api.py` + `api_models.py`: FastAPI with strict Pydantic response models. See [web-app.md](web-app.md).

## `guide/`
The user-facing documentation, in Danish: `brugervejledning/` (the user guide, page by page) and `laerebog/` (the textbook: the theory behind every reading, with "Sådan gør radaren" sections that describe the code as it is). Served by `guide.py` and rendered on the app's Guide page. `guide/STIL.md` holds the writing conventions (terms, chapter template, placeholders, links). Shipped publicly like the rest of the app. A user-facing change updates its chapter in the same change; `tests/test_guide.py` checks titles, placeholders, links and anchors.

## `web/`
Vite + React + TypeScript app served by `radar serve`: the only UI (the old static `radar.html` is gone). The skills (`/market-brief`, `/research`) don't depend on it; they read `summary.json`.

## Sharing and releases
- This repo is private (its history holds personal briefs). `scripts/publish_public.py` exports HEAD without the paths in `publish/exclude.txt`, adds `publish/overlay/` (the public repo's release and smoke workflows), runs a leak check against `notes/leak-patterns.txt` and the git author, and commits into a clone of the public repo as "Market Radar". Pushing and tagging are manual.
- `marketing/` holds the Danish brochure: the PDF and its sources are committed, the screenshots (`site/img/`) are rebuilt locally. `scripts/marketing.py` builds `.demo/`: a copy of the working tree minus `publish/exclude.txt`, the market data and a database seeded from `marketing/demo/seed.yaml` through the API, so screenshots never see `userdata/`. Shots are cropped by element (`marketing/shots.yaml`), and `check` reuses the public export's leak check.
- A `v*` tag in the public repo builds the release zip (`scripts/build_release_zip.py`: tracked files + prebuilt `web/dist`) that non-technical users download and start with `Start Market Radar.cmd` / `.command` (they install uv if needed, `uv sync`, `radar serve --open`).

## Local vs committed
- `data/`, `reports/`, `imports/*`, `notes/` and `userdata/` are gitignored. They hold local data, personal holdings, the user's own reading notes (`notes/bloomberg.md`, read by `/market-brief`) and their edits from the web app. Unlike `data/`, `userdata/` can't be re-downloaded.
- The rank snapshots in `data/snapshots/` (for "new", "dropped" and "Δ rank") build up locally with each `radar run`; like the rest of `data/` they are not committed.
- The monthly brief runs on this machine: a Claude desktop scheduled task runs `/market-brief` on the 1st (it runs `radar run` itself and reads `notes/`, the views and the latest discovery scan), writing `briefs/YYYY-MM-DD.md`. There is no GitHub workflow in this repo and no CI on pull requests; the public repo has its own release and smoke workflows (`publish/overlay`).
- `radar bundle-holdings` / `unbundle-holdings` carry your portfolios, watchlist edits, market views and vote choices to another machine as one base64 file.
